# VS Code + WSL Markdown 预览空白：远程资源 401 故障分析

## 摘要

在 VS Code 连接 WSL 的开发环境中，可能出现 Markdown 源文件可以正常编辑、内置预览却完全空白的现象。如果开发者工具显示多个预览脚本和样式请求返回 `401 Unauthorized`，故障可能位于 Webview 的远程资源访问校验，而不是 Markdown 内容本身。

本文分析一种已通过实际排查和绕过验证的故障机制：**WSL 远程连接标识的大小写与 Webview 资源 URL 中的标识不一致，导致严格比较失败，进而触发资源访问拒绝。**

本文提供通用的诊断流程、代码层面的解释及低影响解决方案，不依赖特定用户名、项目目录或安装路径。

> 适用边界：相关校验逻辑在 VS Code 1.141.1 的实际案例中得到检查。本文不是全部受影响版本清单，也不意味着所有 Markdown 空白预览或所有 401 都由此原因造成。

## 1. 故障特征

典型表现如下：

- WSL 连接正常，Markdown 源文件可以打开和编辑。
- 内置 Markdown 预览标签页能够创建，但正文区域完全空白。
- 开发者工具中，多个预览资源请求返回 401。
- 失败资源可能来自 Markdown、数学公式、图表等不同内置扩展。
- 使用全小写的远程连接标识重新打开项目后，预览恢复。

示意错误：

```text
GET https://…vscode-resource…/extensions/markdown-language-features/…
net::ERR_ABORTED 401 (Unauthorized)
```

单独出现“空白预览”不足以判定根因。需要结合资源错误、连接标识及实际校验逻辑进一步判断。

## 2. 理解故障所在的层次

Markdown 源文件编辑和预览不是同一条处理链路。

```text
源文件编辑：
远程文件系统 → 编辑器文本缓冲区

Markdown 预览：
远程文件系统 → Markdown 扩展 → Webview 页面
                                   ↓
                        脚本、样式和图片资源加载
                                   ↓
                              页面显示与交互
```

因此：

- 源文件可读，只说明正文读取链路可用。
- 预览面板存在，不代表其 JavaScript 和 CSS 已成功加载。
- 文章能被其他 Markdown 工具或静态站点构建器处理，也不能证明 VS Code 的 Webview 链路正常。

这种分层有助于避免一开始就修改正文、文件权限或重装 WSL。

## 3. 通用排查流程

### 3.1 确认使用的是内置预览

在 Markdown 源文件中打开命令面板，执行：

```text
Markdown: Open Preview to the Side
```

明确选择内置预览，可以避免把第三方 Markdown 编辑器的问题与 VS Code 自带功能混在一起。

如果某个第三方扩展出现在激活日志中，只能说明它参与了当前会话，不能证明它导致故障。应通过对照测试判断，而不是立即卸载。

### 3.2 用最小文件缩小范围

新建一个仅包含以下内容的 Markdown 文件并预览：

```markdown
# Preview test

Hello, Markdown.
```

- 最小文件正常：继续检查原文内容、资源引用或特定渲染扩展。
- 最小文件也空白：优先检查预览基础设施和运行环境。

这是推荐的通用诊断步骤，不是仅凭复杂文章的表现推断结论。

### 3.3 检查扩展状态和配置

重点检查：

- 内置 `vscode.markdown-language-features` 是否启用、是否成功激活。
- 是否存在预览相关的激活异常。
- 用户、远程和工作区设置是否覆盖了 Markdown 的打开方式。
- 当前实际连接的 WSL 发行版和远程用户是否符合预期。

可以通过命令面板查看日志：

```text
Developer: Show Logs...
```

根据 VS Code 版本选择窗口或远程扩展宿主相关日志。日志名称和目录结构可能随版本变化，优先使用界面入口，不要依赖固定磁盘路径。

如果直接检查 WSL 文件系统，应先确认服务实际运行用户；项目所属目录不一定等于 VS Code Server 的运行用户目录。

### 3.4 查看 Webview 的资源错误

执行：

```text
Developer: Toggle Developer Tools
```

在开发者工具中：

1. 打开 Console。
2. 保持工具开启，关闭并重新打开 Markdown 预览。
3. 查看新增错误；必要时结合 Network 面板检查失败请求。
4. 记录状态码、请求资源类型和远程连接标识。

重点区分不同失败模式：

| 表现                       | 优先调查方向                                 |
| -------------------------- | -------------------------------------------- |
| 多个脚本和样式均返回 401   | Webview 资源准入校验、远程标识、允许访问目录 |
| 个别资源返回 404           | 资源路径、文件是否存在、安装是否完整         |
| 脚本加载成功后出现运行异常 | 渲染脚本、Markdown 内容或扩展兼容性          |
| 明确的 CSP 拒绝信息        | 内容安全策略和被阻止的资源类型               |
| Service Worker 注册失败    | Webview 初始化或浏览器存储状态               |

这些是调查方向，不是看到某个状态码就可以直接下结论。

### 3.5 从共同失败点寻找根因

如果 Markdown、数学公式、图表等不同扩展的资源同时返回 401，优先调查它们共用的资源加载机制。

不要把控制台中最显眼的警告自动当成根因。例如，功能策略警告与资源 401 同时出现时，应优先追踪能够直接解释脚本加载失败的错误链。

## 4. 根因机制：远程标识大小写不一致

以下使用 `Ubuntu-20.04` 作为连接名称示例，具体发行版名称并不是故障机制的必要条件。

### 4.1 两种表示形式

VS Code 窗口的远程连接标识可能是：

```text
wsl+Ubuntu-20.04
```

Webview 将远程资源映射到 HTTPS URL。连接标识被编码进主机名后，浏览器的主机名规范化会影响大小写。示意形式为：

```text
vscode-remote+wsl-002bubuntu-002d20-002e04.…
```

其中 `-002b`、`-002d`、`-002e` 分别对应编码后的 `+`、`-`、`.`。相应的远程标识变为：

```text
wsl+ubuntu-20.04
```

于是出现差异：

```js
'wsl+Ubuntu-20.04' === 'wsl+ubuntu-20.04'
// false
```

这里比较的是应用程序中的连接标识，不是 Linux 文件名。不能因此把整个资源路径都转成小写，否则可能破坏 Linux 文件系统的路径语义。

### 4.2 严格比较影响远程操作系统信息获取

在所检查版本中，资源加载流程只有在请求标识与当前连接标识严格相等时，才获取用于路径校验的远程操作系统信息。

以下为简化的逻辑示意，不是源码逐字引用：

```js
const remoteOS =
  resource.scheme === 'vscode-remote' && connection?.remoteAuthority === resource.authority
    ? (await remoteAgentService.getEnvironment())?.os
    : undefined
```

当大小写不一致时，`remoteOS` 为 `undefined`。

### 4.3 路径校验拒绝缺少上下文的远程资源

后续校验需要根据远程操作系统规范化路径，再判断资源是否位于允许访问的目录内：

```js
function resolveAllowedResource(resource, roots, remoteOS) {
  if (resource.scheme === 'vscode-remote') {
    if (remoteOS === undefined) return undefined
    // 根据远程操作系统规范化路径，并检查允许目录。
  }
  // ...
}
```

没有可加载路径时，结果为 `AccessDenied`：

```js
const resourceToLoad = resolveAllowedResource(resource, roots, remoteOS)
if (!resourceToLoad) return AccessDenied
```

Webview 响应流程再把这个结果转换成 401：

```text
标识大小写不一致
    ↓
严格比较失败
    ↓
remoteOS 未取得
    ↓
远程资源校验不返回可加载路径
    ↓
AccessDenied
    ↓
401 Unauthorized
    ↓
预览脚本和样式加载失败
    ↓
空白预览
```

### 4.4 为什么不是“账号没登录”

HTTP 状态码 401 通常让人想到身份认证，但在此机制中，响应由 VS Code 的 Webview 内部资源访问流程生成。

因此，不能仅凭这里的 401 就要求用户：

- 登录 GitHub；
- 修改网站密码；
- 执行 `chmod` 放宽文件权限；
- 关闭代理或 Webview 安全限制。

必须先确认响应来自哪个组件，再判断需要修复什么。

## 5. 如何验证这一判断

建议同时收集三类证据：

1. **运行日志**：当前窗口的远程连接标识包含大写字符。
2. **资源请求**：失败 URL 对应的连接标识与当前窗口只存在大小写差异。
3. **行为对照**：同一文件在全小写连接下恢复预览。

为了区分“改变标识有效”与“新建窗口偶然恢复”，可以在保存工作后进行对照：

| 测试                   | 保持不变的条件         | 观察目标               |
| ---------------------- | ---------------------- | ---------------------- |
| 使用原标识新建窗口     | 项目、文件、扩展、版本 | 是否仍然返回 401       |
| 使用全小写标识新建窗口 | 项目、文件、扩展、版本 | 是否恢复资源加载与预览 |
| 再次使用原标识         | 同上                   | 是否稳定复现           |

不需要为验证而删除缓存、修改正文或重装服务，以免引入额外变量。

实际案例中，全小写连接方案已恢复预览，并有日志、请求截图和代码逻辑支持；但未完成上述完整往返实验，也未进行运行时断点验证。因此，不应把单次恢复推广为对所有类似故障的证明。

## 6. 解决方案

### 6.1 使用全小写连接标识

在 Windows PowerShell 中确认发行版名称：

```powershell
wsl --list --quiet
```

然后以全小写远程标识打开项目。以下示例中的发行版和项目目录需要按实际环境替换：

```powershell
$Distro = 'Ubuntu-20.04'
$Project = '/path/to/project'
$Remote = 'wsl+' + $Distro.ToLowerInvariant()

code --new-window --remote $Remote $Project
```

`$Project` 是 WSL 内部的 Linux 路径。此方法改变的是 VS Code 连接入口，不是重命名发行版，也不是修改项目路径。

若 `code` 命令不可用，可使用 Windows VS Code 命令行启动器的完整路径执行同样的参数。

### 6.2 避免每次输入命令

确认预览恢复后，可以：

- 从“最近打开”中使用新生成的项目记录，避免复用旧的大小写不一致入口。
- 建立带固定小写 `--remote` 参数的快捷方式或启动脚本。
- 关闭旧窗口，避免误以为已经切换到新的连接会话。

不同版本对历史记录的处理可能不同。如果重新启动后旧记录仍复现问题，固定参数的启动入口更容易验证和维护。

### 6.3 长期处理

关注 VS Code 和 WSL 扩展的相关修复，并在升级后验证原入口是否恢复。

不建议直接修改安装目录中的压缩 JavaScript，更不应跳过资源安全校验。合理的软件修复需要兼顾连接标识的等价规则与远程路径的安全语义，而不是简单把所有字符串转成小写。

## 7. 如何判断是否由更新引入

“以前正常，现在失败”说明环境或状态发生过变化，但不足以证明是哪一次更新导致。

可能变化包括：

- VS Code 调整了远程资源校验流程。
- WSL 扩展或启动入口改变了连接标识的大小写。
- 历史项目记录保存了不同形式的远程地址。

要进一步认定版本回归，应记录：

- 当前与此前正常的 VS Code 版本。
- WSL 扩展版本。
- 两种情况下的连接标识和打开方式。
- 同一文件在对应版本中的对照结果。

在缺少这些证据时，应将“更新引入”标为待验证假设，而不是已确认事实。本文不宣称某个版本是首次引入故障或首次修复故障的版本。

## 8. 排查经验

### 先定位层次，再选择工具

源文件读取问题看文件系统和远程连接；扩展激活问题看扩展宿主日志；Webview 空白问题则应尽早查看浏览器控制台和资源请求。

### 区分相关线索与因果证据

第三方扩展被激活、控制台出现警告、日志中有其他错误，都不自动构成根因。优先寻找能解释全部现象，并能通过低影响实验验证的机制。

### 多项资源同时失败，先找公共路径

不同功能的资源同时出现同类错误时，通常应先检查共享的加载和校验层，而不是分别修复每一个扩展。

### 状态码必须结合产生位置解释

内部资源代理返回的 401，与外部服务要求登录，不一定是同一种问题。追踪状态码从何而来，比按字面猜测更可靠。

### 保持修复最小化

连接入口能解决的问题，不应先升级为删除配置、重装 WSL、放宽权限或关闭安全机制。先用最少变量验证，再决定是否需要更大范围的变更。
